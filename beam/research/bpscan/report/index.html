The bug

One line in the wrong order

The inner-product argument folds the proof over 6 rounds. Each round the prover publishes two points, Li and Ri, and the verifier derives a challenge xi by hashing the transcript. A point is locked in only if it enters the hash before a challenge is derived from it.

challenge xi (transcript hash) L/R locked by a later challenge L/R locked by nothing

Fix: commit 37ca7d8ca "BP scheme upgraded" in core/ecc_bulletproof.cpp, XSet::NextChallenge(…, iVersion). Since HF6, nodes accept v1 proofs only.

Lustration · BIP-5 · HF7

The only real answer, and its blind spot

Just before HF7, each node snapshots a per-asset Total (emission + treasury + issued CA − deposits − funds locked in contracts). Every output created before HF7 must disclose its amount the first time it is spent, and disclosures add up in Consumed. A block that pushes Consumed past Total is rejected. A negative output can never disclose, because the amount must be a uint64.

All values are % of Total. This illustrates the mechanism; it is not a forecast.

Method

How the numbers were produced

  1. Source. A fully synced explorer node (no TxoLo/TxoHi horizons). The Txo table holds every output with its full proof, and the kernels in States.Ethernal hold the shielded outputs.
  2. Snapshot. The node kept running. We copied the live file, then re-copied changed 1 MB chunks until a pass saw no commit, and confirmed it with PRAGMA quick_check.
  3. Coverage. 39,657,830 TXO rows of 43,777,945 ids. The gap of 4,120,115 is exactly one reserved id per block. Heights 1 … 4,120,114 are contiguous.
  4. Control. Post-HF6 proofs (sound scheme) must score zero. They did.

Reproduce

cmake -S <beam-src> -B build -G Ninja \
  -DCMAKE_BUILD_TYPE=Release -DBEAM_IPFS_SUPPORT=OFF \
  -DBPSCAN_DIR=$PWD -DCMAKE_PROJECT_INCLUDE=$PWD/inject.cmake
ninja -C build bpscan
python3 resync.py live/node.db copy/node.db
bpscan copy/node.db out/ --check
bpscan copy/node.db out/
