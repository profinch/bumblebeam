# 3BMiner

Open firmware for ESP32 boards that mines Bitcoin solo (a lottery: an ESP32 will not find a block in
any human lifetime) and keeps whatever else the board was bought for, a camera for a start. ESP-IDF
5.3, no Arduino. It speaks the NMMiner HTTP API, so NMMiner's monitor and swarm pages see it as one of
theirs.

The SHA-256 engine of the classic ESP32 is driven by a cycle-scheduled Xtensa kernel on core 0 with
interrupts off; core 1 keeps Wi-Fi, the web server, the camera and a software hasher
(nerdSHA256plus) for its idle time.

| Board | Profile | What it does | Measured |
|---|---|---|---|
| ESP32-WROOM-32 devkit (ESP32-D0WD-V3) | [`boards/devkit`](boards/devkit) | miner | ~952 KH/s engine + ~29 KH/s software = **~981 KH/s**, 252 cycles/nonce |
| AI-Thinker ESP32-CAM + ESP32-CAM-MB (OV2640, 4 MB PSRAM) | [`boards/esp32cam`](boards/esp32cam) | camera (everything Espressif's CameraWebServer does), miner off by default | stream 50 fps at 320x240, 25 at 640x480, 10 at 1280x720, 3.6 at 1600x1200 |

For scale: NerdMiner v2 does ~350 KH/s on the same chip, NMMiner (closed, paid license on boards
other than its own) ~1.03 MH/s. Over 7.6 h side by side on one pool (fw 0.5.2 against NMMiner
v2.0.04): 3BMiner 982 KH/s on the device and 1002 KH/s by the pool's estimate against NMMiner's
1036 and 999, 3127 accepted shares to 3016, rejects 0.95% to 1.34%, no restarts on either.

## One source, one version, a build per board

As NerdMiner and NMMiner do it: every board gets its own image, all of them from this tree and under
one version number (`main/version.h`). A board profile is a `boards/<id>/sdkconfig.defaults` that
picks the board in `main/Kconfig.projbuild` (pins, PSRAM, which modules are built in, the default
for mining). Each image carries `3BMINER_BOARD=<id>;`, and the OTA upload refuses an image built for
another board.

```sh
. ~/esp/esp-idf/export.sh
tools/build.sh devkit        # -> dist/3bminer-devkit-<version>.bin
tools/build.sh esp32cam      # -> dist/3bminer-esp32cam-<version>.bin
```

`build-<board>/` holds each board's sdkconfig; `dist/` gets the app, the bootloader, the partition
table and `ota_data_initial.bin`. Copy `main/secrets.example.h` to `main/secrets.h` for local Wi-Fi
and payout defaults; without it the board starts with empty ones, to be set in the web UI.

## Flash

First time, over USB:

```sh
esptool.py --port <port> --baud 460800 write-flash 0x1000 dist/bootloader-<board>.bin 0x8000 dist/partition-table.bin \
    0xe000 dist/ota_data_initial.bin 0x10000 dist/3bminer-<board>-<version>.bin
```

Afterwards over Wi-Fi from the Firmware page or `curl -X POST --data-binary @dist/3bminer-<board>-<version>.bin http://<ip>/update`.
`partitions.csv` has two 1.875 MB app slots, so the previous version stays on the board.

The CH340 on some ESP32-CAM-MB adapters works with the Windows driver for exactly one port
reconfiguration after the port is opened (error 31 "device not functioning" after that), which
breaks esptool and the Arduino IDE. [`tools/esptool_ch340fix.py`](tools/esptool_ch340fix.py) sets 115200 once and ignores
the later errors: `py -3 tools/esptool_ch340fix.py --port COM7 --baud 115200 <esptool command>`.

## HTTP API

| Path | What |
|---|---|
| `/` | dashboard; `/camera` on camera boards |
| `/probe`, `/alive`, `/api/system/info`, `/api/system/restart`, `/api/swarm/find` | NMMiner-compatible; `info` adds the engine/software split, kernel cycles, reject reasons, reset reason, board id |
| `GET/POST /api/config` | Wi-Fi (with an optional BSSID lock), pool, address, worker, start difficulty, `mining` on/off |
| `POST /update` | raw image, written to the spare slot |
| `/api/bench?k=&t=&n=` | engine check on the board: a fixed header, every hit re-checked in software (mining pauses for it) |
| `/capture`, `/bmp`, `/status`, `/control?var=&val=`, `/xclk`, `/reg`, `/greg`, `/pll`, `/resolution`, `:81/stream` | camera boards: the CameraWebServer API, same names and parameters |
| `POST /api/camera/save` | keep the camera settings across restarts |

## Layout

- `main/mine.S`, `main/mine2.S` the kernels; `mine2.S` is generated by `tools/gen_mine2.py` (START of
  block 1 after K header words, the hit test of nonce N-1 inside the engine wait of nonce N). The
  default is K=6 with waits 25/36/23/6/8 (`main/miner.c`).
- `main/miner.c` core-0 mining task, genesis self-test at boot, on-board bench, core-1 software task.
- `main/stratum.c` stratum v1: keeps the last jobs so a share for a job replaced without `clean` still
  goes out, sorts rejects by the pool's error code.
- `main/camera.c` camera boards: esp32-camera, flash LED, the CameraWebServer API, settings in NVS.
- `main/web.c`, `main/www/` web server and pages (gzipped by the build, ~11 KB in the image).
- `web-next/` the next web UI (menu like the pool's, swarm scan, settings, display previews), not in
  the firmware yet; plans in [`web-next/ROADMAP.md`](web-next/ROADMAP.md).

## What the engine and the chip allow (measured)

- A block takes ~66–70 cycles and the engine reads its input as a stream (~1 word per cycle), so the
  next block can be written behind its read pointer. START after 6 words works, after 5 never does.
  LOAD needs ~6–8 cycles before TEXT is valid; BUSY lags right after START, so the kernel counts
  cycles instead of polling. The ESP32 engine cannot load a midstate: three blocks per nonce, and
  that, not the code, is the ceiling (~0.95–1.0 MH/s).
- Stores to the engine cost ~2 cycles from asm and ~7 from C (MEMW after volatile stores). A load
  feeding a `loopnez` right away stalls: the wait counts are loaded early.
- mbedtls uses the same engine and switches its clock off: `CONFIG_MBEDTLS_HARDWARE_SHA=n`.
- Code in IRAM on core 1 slows the core-0 kernel from 252 to ~370 cycles (shared SRAM banks); the
  software hasher runs from flash, where it costs the engine nothing.
- The camera driver's grab task runs at Wi-Fi's priority and, in latest-frame mode, copies every
  frame to PSRAM with the CPU even with nobody watching. On core 1 next to Wi-Fi that made the network
  take seconds per request; it is lowered under lwip and grabs only on demand.
